## 3. Call stack

**Retire.** `VendorsList` Retire (arms `retireCandidateId`, shows `vendor.productCount`) → Confirm →
`deactivateVendorAction` → `requireRole("owner","manager")` → `vendorIdSchema.parse` →
`catalog.deactivateVendor` → `db.transaction` → `assertVendorOwned` (NotFound if cross-tenant) →
`UPDATE vendor SET active=false WHERE id AND organization_id` → active-product `COUNT` →
`{vendorId, productCount}` → `runAction` → `router.refresh()`.

**Reactivate.** Same chain through `reactivateVendorAction` → `reactivateVendor`, `active=true`. The armed text uses the row's `productCount`.

**Stale product save.** `ProductEditForm` submit (vendor unchanged → `vendorId` omitted; changed → sent) →
`updateProductAction` → `catalog.updateProduct` → `db.transaction` → if `patch.vendorId != null`:
`assertVendorActive` (first statement) → `assertProductOwned` → patch and par writes. A throw rolls back; the form shows `err.message`.
`createProduct`: guard before the insert.

**Bulk assign.** `assignVendorToProductsAction` → `assignVendorToProducts` → transaction →
`assertVendorActive` (moved above the product-ownership select) → product select → `UPDATE product`.

**Invoice upload.** `uploadInvoiceAction` → `createInvoiceForUpload` → `findLiveCopy` (read-only, before the tx) →
`db.transaction` → `assertVendorActive` → insert. A duplicate file returns `duplicate` without the vendor check (nothing is written).

**Invoice review, vendor retired (unguarded).** Detail page: `listAllVendorsAction` → vendor `active=false` → `InvoiceReviewForm vendorRetired` → informational note only; Submit and Approve stay enabled.
Submit: `reviewInvoiceAction` → `submitInvoiceReview` → `withLockRetry` → transaction → `applyLineReviewTx` → CAS → `learnAliasesTx` → `upsertAliasCore` — all unchanged, no vendor check.

**Approve, vendor retired (unguarded).** `approveInvoiceAction` → `approveInvoice` → unchanged: lock, replay check, status check, zero-line check, status write and cost posting. `product_cost_history` rows are written and products still linked to the vendor get the new cost.

**Reorder.** `reorderList` → products query → vendor query `{id, name, active}` → items get `vendorActive` →
sort (retired first, vendor name, product name) → `reorder/page.tsx` groups by `vendorId` →
a group with `vendorActive=false` renders `<ReorderVendorBlock flagged>` first.

**Name reuse.** `createVendorAction` → `createVendor` → insert → duplicate key → `SELECT active FROM vendor WHERE organization_id AND name` →
retired ? `DomainError("VENDOR_NAME_RETIRED")` : `ConflictError(vendorNameTaken)`. `updateVendor` does the same in its update catch.

## 4. Test plan

DB = needs the `_test` database (`bun run test`). Browser = Playwright or `verify-browser.mjs`. Helpers: `tests/helpers/test-db.ts` (`createFixtures`: `owner`, `manager`, `staff`, `otherOwner`, `vendorId`, `otherVendorId`, products, invoice fixtures).

**`tests/vendor-retire.test.ts` (DB)**

- `deactivateVendor sets active=false and returns the count of active products only` — an inactive product on the vendor is not counted.
- `deactivateVendor and reactivateVendor are idempotent` — second call succeeds, row unchanged.
- `retire / reactivate on another tenant's or a nonexistent vendor id is NotFound, row untouched` (invariant 9) — never says "retired".
- `retiring keeps products linked` — `product.vendor_id` unchanged (Gate 1 decision 1).
- `each guarded write refuses a retired vendor with VENDOR_RETIRED and writes nothing`, one case per write (four), asserting the tables afterwards:
  1. `createProduct` — no product row inserted
  2. `updateProduct` with `vendorId` — name and par in the same patch are not saved
  3. `assignVendorToProducts` — no product changed, with several ids
  4. `createInvoiceForUpload` — no `invoice` row
- `an invoice in review whose vendor is retired can be submitted and approved, and its costs post` — create the invoice in `needs_review`, retire the vendor, `submitInvoiceReview` then `approveInvoice` succeed; status `approved`, `product_cost_history` rows exist.
- `alias learning still records aliases for that invoice` — after the submit above, the `vendor_alias` rows exist for the retired vendor.
- `rejectInvoice on an invoice of a retired vendor still works` — unchanged behaviour, pinned.
- `guard runs above other lookups` — **decided:** `updateProduct` with a retired vendor and a nonexistent product id throws `VENDOR_RETIRED`, not `NotFound("Product")`; `assignVendorToProducts` with a retired vendor and a foreign product id also throws `VENDOR_RETIRED`. This is invariant 6 ("above any existing-row lookup"). Companion case: a cross-tenant vendor id with a nonexistent product still throws `NotFound("Vendor")`, so nothing about another tenant leaks.
- `clearing the vendor (vendorId: null) is allowed` for `updateProduct` and `assignVendorToProducts`, including when the current vendor is retired.
- `a save that leaves vendorId out succeeds for a product linked to a retired vendor` — par/name change, link kept.
- `race: retire in an open tx makes a concurrent product write block, then fail` — tx A updates `vendor.active=false` uncommitted; B (`updateProduct`) starts and blocks on `FOR UPDATE`; commit A; B rejects `VENDOR_RETIRED`; product unchanged. Mirror: B holds the lock first, A's retire waits, then every later write is refused.
- `success metric: nothing gains the retired vendor after retirement` — attempt all four guarded writes against the retired vendor; afterwards the count of products and invoices pointing at it equals the count taken at retirement (aliases are excluded: learning on an in-review invoice is allowed).
- `name reuse: create or rename to a retired vendor's name is VENDOR_NAME_RETIRED; an active duplicate keeps the existing ConflictError message` — the existing case in `vendor-write-path.test.ts` stays untouched and must still pass.
- `reactivate returns the vendor to listVendors and the guard accepts it again`.
- `listVendors is active-only by default; includeInactive returns both with correct active and productCount` — inactive products and other tenants' vendors excluded.
- `reorderList sorts retired-vendor items first and sets vendorActive` — `true` for vendorless items.
- `audit packet still names a retired vendor` — approve an invoice, retire the vendor, build the packet; the name is present.
- `invoices of a retired vendor stay readable` — `listInvoices` filtered by `vendorId` still returns them.

**`tests/vendor-retire-actions.test.ts` (DB, mocked auth)**

- `staff is refused on listAllVendorsAction, deactivateVendorAction and reactivateVendorAction — row unchanged`.
- `manager and owner can retire and reactivate`.
- `a retired vendor is absent from listVendorsAction and present in listAllVendorsAction`.
- `VENDOR_RETIRED and VENDOR_NAME_RETIRED messages reach the client verbatim` (`ok:false`, message names the vendor).

## 5. Least confident decisions

1. **The guard lives in a new `lib/domain/vendor-active.ts`, not `catalog.ts`** (02 said `catalog.ts`), so `invoices.ts` does not import the huge catalog module. The alternative is a one-line re-export from `catalog.ts`.
2. **Guard-first ordering shows "vendor is retired" before "product not found".** It follows invariant 6's wording, but a caller with a bad product id and a retired vendor sees the vendor message.
3. **"Send `vendorId` only when changed" is a client contract.** A stale or hand-built client that sends the unchanged retired id is refused (Decision B accepted this); the tests pin both sides.
4. **Reorder grouping changes from vendor name to `vendorId`**, so a retired vendor and an active one never merge by name. Safe because names are unique per org, but any other consumer grouping by name would diverge.
5. **`productCount` is a correlated subquery on every `listVendors` call**, including the active-only picker path that ignores it. Cheap at tens of vendors; revisit if vendors grow.
6. **The race test relies on InnoDB lock waits** and may be flaky under load; Bun's 5 s per-test limit needs a tight wait or `--timeout`.
7. **Approving an in-review invoice of a retired vendor updates cost on products still linked to it.** This is intended (owner decision 2026-11-09: the prices are real), but a flagged "Retired vendor" product's cost can still move until the manager reassigns it; the reorder flag and the catalog marker are unaffected.
