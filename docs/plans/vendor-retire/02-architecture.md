# Gate 2 — Architecture: retire a vendor

Read against the code at `103f4ba` (2026-11-09). Spec: `01-product.md`
(APPROVED). Model: the location retire path (`deactivateLocation`,
`LOCATION_RETIRED` in `scanCountLineTx`, `listLocations({includeInactive})`).

**Headline:** one column (`vendor.active`), migration **0013**. Two new server
actions (retire, reactivate), no route handlers. One new domain guard,
`assertVendorActive`, called from every write path that stores a `vendor_id`.
Reads default to active-only; screens that only *display* a vendor's name ask
for retired vendors too.

Three facts in the code shaped this (each verified 2026-11-09):

1. **The product edit form always sends `vendorId` on save**
   (`components/office/product-edit-form.tsx:156`). A write path that refuses
   every retired vendor would make a product still linked to one unsavable —
   even to fix its par. See Flow 3 and Decision B.
2. **The catalog table shows no vendor today.** "The catalog marks it" is new
   display work, not a marker on something that exists.
3. **Error codes do not reach the browser.** `runAction`
   (`lib/action-result.ts:45`) forwards only `err.message`. The UI shows the
   message text (the Gate 1 wording) and does not branch on the code.

`requireRole("owner","manager")` inside the action (invariant 7), matching

## Data

**Migration 0013:** `ALTER TABLE vendor ADD active boolean NOT NULL DEFAULT
true`. Existing rows become active. No index: every vendor read already filters
on `organization_id` (`vendor_organization_id_idx`) and a tenant has tens of
vendors. No other schema change — `vendor_organization_name_unique` already
keeps a retired name taken; the product and invoice FKs stay, since retiring
never deletes.

**Error codes** (`DomainError(code, message)`, message shown verbatim):

- `VENDOR_RETIRED` — *"{name} is retired. Choose another vendor, or reactivate
  it on the Vendors screen."*
- `VENDOR_NAME_RETIRED` — *"A retired vendor already uses this name —
  reactivate it instead."*
- Another tenant's or a nonexistent id stays `NotFoundError("Vendor")`, never
  "retired" (invariant 9).

**Queries:**

- **`assertVendorActive(tx, orgId, vendorId) → {id, name}`** — `SELECT id,
  name, active FROM vendor WHERE id=? AND organization_id=? FOR UPDATE`. No row
  → NotFound; `!active` → `VENDOR_RETIRED`. A *locking* read on purpose: a plain
  snapshot read would let a retire that commits mid-transaction slip past.
- **`assertInvoiceVendorActiveTx(tx, actor, invoiceId)`** — `SELECT
  invoice.vendor_id … FOR UPDATE` (org-scoped; no row → NotFound), then
  `assertVendorActive` if non-null. An invoice with no vendor passes.
- **`listVendors(actor, {includeInactive})`** — vendor rows plus a correlated
  `COUNT(*)` of *active* products with that `vendor_id` (uses
  `product_vendor_id_idx`). **This is where the confirmations' "12 products"
  comes from** — it is on the row when the screen renders, so the first tap
  needs no server call; retire/reactivate return a fresh count.
- **`deactivateVendor` / `reactivateVendor`** — one transaction: ownership lock,
  `UPDATE vendor SET active=? WHERE id=? AND organization_id=?`, the count.
  Idempotent. No guard beyond ownership — Gate 1 Decision 1 allows retiring
  while products use it.
- **Name collisions** (`createVendor`, `updateVendor`) — still caught as a
  duplicate key on the unique index; only on that failure path, `SELECT active
  FROM vendor WHERE organization_id=? AND name=?` (same collation as the index)
  decides `VENDOR_NAME_RETIRED` vs the existing conflict. Happy path unchanged;
  the database still enforces uniqueness.
- **`reorderList`** — the existing vendor select adds `active`; sort is
  (retired first, vendor name, product name). Still three queries.

**Writes guarded by `assertVendorActive`, each inside its existing transaction,
before any other row lookup** (verified line numbers, `103f4ba`):

1. `createProduct` — `catalog.ts:660`, before the insert.
2. `updateProduct` — `catalog.ts:822`, **moved above** `assertProductOwned`
   (line 818), when `patch.vendorId` is non-null.
3. `assignVendorToProducts` — `catalog.ts:1413`, **moved above** the
   product-ownership select (~1395), when non-null.
4. `createInvoiceForUpload` — `invoices.ts:443`, before the insert
   (`findLiveCopy` before the transaction only reads and returns).
5. `submitInvoiceReview` — `invoice-lines.ts:568`, first statement, above
   `applyLineReviewTx`: no line corrections, no CAS to `reviewed`, no alias
   learning for a retired vendor.
6. `approveInvoice` — `invoice-approval.ts:144–163`, after the
   already-approved replay branch, before the status write and cost posting.
7. `upsertAliasCore` — `matching.ts:232`, before the insert (backstop).

Clearing a vendor (`vendorId: null`) is never refused.

## Flow — main paths

1. **Retire.** Vendors screen (`listAllVendorsAction`, row has `productCount`)
   → Retire arms the row: *"12 products still use this vendor — they will need
   a new one."* → Confirm → `deactivateVendorAction` → `requireRole` → parse →
   `deactivateVendor` → `router.refresh()`. Row shows Retired + Reactivate.
2. **Reactivate.** Retired row → Reactivate arms it: *"Reactivate X? It will
   appear in every vendor list again, and 3 products assigned to it will stop
   being flagged."* → Confirm reactivate? → `reactivateVendorAction` → refresh.
3. **A screen opened before the retire.** Product edit form still lists the
   vendor → Save → `updateProduct` → `assertVendorActive` throws before
   `assertProductOwned` → transaction rolls back → form stays open showing the
   message. Bulk assign and invoice upload behave the same.
   *Form change:* send `vendorId` only if the user changed it; the detail page
   passes active vendors plus the product's current vendor labelled
   "(retired)" so the select can show it.
4. **Invoice from a retired vendor** reaches `needs_review` as usual. Detail
   page sees `active=false` → hold banner + Submit disabled. A stale Submit →
   refused as the first statement, nothing written. Already `reviewed` →
   `approveInvoice` refuses, no `product_cost_history` row. Remedies:
   reactivate, or reject the invoice.
5. **Reorder.** Items with `vendorActive=false` sort first → one flagged block,
   vendor column, "Open in catalog", no Copy/Print (it is not an order for
   anyone). Normal vendor blocks follow.
6. **Name reuse.** Create "Southern Glazer's" → duplicate key → row is retired
   → `VENDOR_NAME_RETIRED` on the form.

## Decisions worth challenging (answer at this gate)

- **A. `listVendorsAction` becomes active-only**; name lookups move to a new
  `listAllVendorsAction`. Alternative: keep it returning everything and filter
  in each picker — safer for name lookups, weaker for future pickers.
  *Recommended: as drafted.* Risk: a missed caller shows `Vendor #12`; all six
  callers are listed in Fit and an e2e check on the invoices list covers it.
- **B. Edit form sends `vendorId` only when changed**, keeping the domain
  refusal unconditional. Alternative: the domain treats a `vendorId` equal to
  the product's current vendor as "no change" and allows it — robust to stale
  clients, but it is an exception inside the guard. *Recommended: as drafted.*
- **C. `FOR UPDATE` on the vendor row in every guarded write** — stricter than
  the location model's plain read; serialises writes per vendor, harmless at
  bar scale. *Recommended: as drafted* — it is what makes "zero assignments
  after retirement" hold under a race.
- **D. Invoice review hold refuses the whole submit**, line corrections
  included. Alternative: allow saving corrections, refuse only the move to
  reviewed/approved. *Recommended: as drafted* (simpler; reject still works).
- **E. Catalog marker built client-side** from the all-vendors list.
  Alternative: a `vendor_retired` reason in the existing "Needs attention"
  filter — easier bulk reassignment, needs a join in product summary queries.
  *Recommended: as drafted for now;* the reorder block's "Open in catalog" is
  the reassignment path.
- **F. `productCount` counts active products only**, via a subquery in
  `listVendors`.

## Risks at this level

1. The default flip in `listVendorsAction` (Decision A).
2. Without the locking read, the success metric is open to a race. Test: retire
   inside an open transaction while a product write waits; the write must fail.
3. Held invoices can pile up if a vendor with invoices in review is retired.
   The banner names both remedies; nothing is auto-rejected.
