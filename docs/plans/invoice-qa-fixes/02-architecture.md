# Gate 2 — Architecture: trustworthy invoice approval

Covers F1, F6 and F7 from `docs/qa/2026-11-06-invoice-failures-handoff.md`. Owner
decisions are recorded in `00-status.md` and are not re-argued here. Written after
reading the code named below.

## Fit

| Module | Change |
|---|---|
| `lib/domain/cost-derivation.ts` | One pure rule decides whether a line posts and, if not, why. Used by the preview and by approval, so they cannot disagree. Has no server imports, so the browser can run it. |
| `lib/domain/invoice-approval.ts` | Reads every line, not only matched product lines. Returns a posting report. |
| `lib/domain/invoice-lines.ts` | `applyLineReviewTx` accepts a pack size, and learns aliases for lines with no item code. |
| `lib/domain/matching.ts` | Builds the alias key. Pre-match uses it and fills in a remembered pack size. |
| `lib/domain/invoices.ts` | Duplicate check at upload request, at confirm, and at resend. Reject releases the file's claim. |
| `app/actions/invoices.ts`, `lib/validation/invoices.ts` | New report read, `packSize` on a correction, duplicate result on upload and confirm. |
| `components/office/invoice-review-form.tsx` | Units-per-case input, the "will post" panel, the posted and skipped panel. |
| `components/office/invoice-upload-form.tsx` | The duplicate refusal, naming the original. |
| `db/schema.ts` | Two nullable columns, one unique index (see Data). |

Nothing changes in the count path, auth, or the extraction parser.

## Endpoints

No new routes. Server actions:

- `approveInvoiceAction` (changed): owner only. Returns the posting report as well as
  the invoice.
- `getInvoicePostingReportAction` (new): owner only, org-scoped. Used by the review
  page, so a reload or a later visit shows the same posted and skipped list.
- `reviewInvoiceAction` (changed): a correction may carry `packSize`.
- `uploadInvoiceAction`, `confirmUploadAction` (changed): can return a structured
  `duplicate` result. It has to be a result, not a thrown `DomainError`, because
  `ActionResult`'s error shape carries only a message and the screen needs the
  original's details.

## Data

One migration per finding, generated by drizzle-kit. All additive and nullable, so
existing rows need no rewrite.

**`vendor_alias.pack_size INT NULL` (F1).** The remembered units per case. It lives
on the alias because the alias is already "this vendor's item", and F6 gives every
line one. `product.case_size` stays out of it, since it is NULL for liquor by design.

- Read: `matchLinesToProducts`' existing batched select, no new query.
- Write: `upsertAliasCore`. When an alias moves to a different product, its pack size
  is replaced, or cleared if none was given. A case size must not follow an item
  code onto a different product.

**`invoice_line.pack_size` stays as it is.** Its schema comment says NULL means "not
determinable, never 1", so `each` = 1 is applied when the cost is derived and is not
stored. This also fixes lines already extracted, with no backfill.

**`vendor_alias.vendor_item_code` is reused for the description key (F6).** No
column change. For a line with no item code the key is `desc:` plus the base64url
SHA-256 of the normalised description: 48 characters, inside the existing
`varchar(64)` and unique index. Hashing is needed because `description` is
`varchar(512)`. Normalising means Unicode NFKC, lower case, collapsed whitespace and
trim. Punctuation and digits stay, so `750ml` and `1.75l` remain different items.
The match method `vendor_alias_desc` already exists in the enum, so no enum change.
A hash is unreadable in the table, but `invoice_line.matched_vendor_alias_id` leads
back to a readable description.

**`invoice.live_file_sha256 VARCHAR(64) NULL` + `UNIQUE (organization_id,
live_file_sha256)` (F7).** The database enforces "one live copy of a file per
organization". `file_sha256` itself can't carry the constraint: its comment says it
is written once and never rewritten, and rejected copies and unverified uploads must
not block anything.

- Set at confirm, in the transaction that moves the job to `queued`, so only bytes
  verified on disk hold a claim. An abandoned upload blocks nothing.
- Cleared when an invoice moves to `rejected`.
- Set again on resend. If another live copy appeared meanwhile, the resend is refused
  and names it. Without this, reject, re-upload, resend gives two live copies.
- Read: a single indexed lookup at upload request, to refuse before any bytes move.
- The unique index, not that lookup, is the guarantee: two simultaneous uploads both
  pass the lookup, and one loses at confirm. A locking alternative was rejected
  because the organization row is a foreign-key parent of nearly every table, so
  `FOR UPDATE` on it would stall unrelated writes.
- Not backfilled. Production has never been deployed, so only dev rows predate it.
  Existing duplicates in dev stay as they are and hold no claim.

## Flow

**F1, review to approval**

1. Extraction runs. Pre-match fills the match and any remembered pack size.
2. The review form runs the shared rule on the current form values, and the panel
   updates as the reviewer types: "3 of 5 lines will update a cost", plus a reason per
   skipped line.
3. Submit moves the invoice to `reviewed`, saving pack sizes on the lines and on the
   alias.
4. On `reviewed`, the same panel shows on the final button.
5. Approve: in one transaction, classify every line, write cost history for those
   that post, then build the report.
6. The report is read from `product_cost_history` by `source_invoice_line_id`, with
   every other line classified for its reason. So "posted" is the rows actually
   written. A replay gets the true numbers instead of today's `costLinesApplied: 0`.

Skip reasons: not matched, deposit or non-product line, no units per case, no
quantity, no net, free goods (net 0), credit (net below 0). A line can only post when
`each` or `keg` gives 1, or a pack size exists.

**F6, second invoice from the same vendor**

Review submit learns an alias from any matched line with a key. On the next upload,
pre-match looks up both kinds of key in the one batched select and sets
`vendor_alias_code` or `vendor_alias_desc`. The form shows "Remembered match" and the
reviewer still confirms it.

**F7, upload**

The browser hashes the file, and `uploadInvoiceAction` looks up a live copy. On a
match, nothing is created and the form shows the mockup. Otherwise the upload goes
ahead, and confirm claims the hash. Losing that race leaves the row at
`awaiting_upload`, the same dead end as any abandoned upload, and the form shows the
same refusal.

## External

None. No new env vars, APIs or webhooks.

## Where this departs from Gate 1

1. **Two clicks stay, not one.** The mockup shows one Approve button. The status
   machine has two steps, `needs_review` to `reviewed`, then `reviewed` to `approved`,
   and `reviewed` is not editable. Both steps will show the counts, and pack sizes are
   entered at the first. A reviewer who notices a problem at the second has to Return,
   which re-extracts and loses their input.
2. **A manager gets the duplicate's details but no link.** The review page is
   owner-only, so "Open invoice" would 404 for a manager.
3. **`keg` counts as 1, like `each`.** Not in the owner's decision, but a keg is one
   unit by the catalog's rule, and the alternative asks for "units per case" on a keg.
4. **`other` or blank units get the same input as `case`.** Better than a dead end.
5. **No vendor on the upload means nothing can be remembered.** The vendor is optional
   at upload and can't be set on the review screen. Those invoices still post, the
   screen says matches won't be remembered, and adding a vendor picker is out of scope.
