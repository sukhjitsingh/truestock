# Adversarial review — Phase 2.5 invoice automation (Gates 2–4)

**Date:** 2026-08-14
**Reviewer:** Codex (adversarial review), branch diff `main...feat/phase-2.5-invoice-automation`
**Verdict:** needs-attention — 3 critical, 4 high
**Scope note:** every finding is in the *approved planning contract*
(`docs/plans/phase-2.5-invoice-automation/02-architecture.md`, `03-program-design.md`,
`04-slices.md`). **No implementation code exists yet**, so nothing shipped is broken.
That is the good news: all seven were free to fix at the time of this review.

Static checks were green when the review ran — `tsc --noEmit`, `eslint`, and the
targeted test files all passed (exit 0). That is exactly the point: **a design defect
does not show up in typecheck, lint, or tests, because there is no code to check yet.**
This repo has been bitten by that shape before (a static CSP returned 200 on every
request while nothing on the page hydrated). Passing gates are not evidence that the
design is sound.

---

## Why these were worth catching at Gate 3 rather than in review of the built code

Five of the seven are the same class of defect this project already codified as
invariants — tenant scoping (9), ownership-vs-existence checks (9), cost visibility (8),
immutability/idempotency of writes (1, 5). The plan re-introduced each one in a new
subsystem. The invariants exist because these failures are **silent**: a cross-tenant
product id resolves to a real row and writes a plausible cost; an unscoped audit ZIP
builds and downloads fine. Nothing errors. The wrongness only surfaces later, in a
number a person trusts.

---

## Findings

### 1. [critical] Invoice originals would be publicly downloadable

**Where:** `02-architecture.md` — external dependency table, "Primary: Local filesystem"
**Claim:** Primary storage was specified as `public/invoices/`.

Next.js serves everything under `public/` as static content, ahead of the application.
No server action, no `requireSession`, no role check, and no organization predicate runs
on that path. Anyone who obtains or guesses a path retrieves a supplier invoice —
containing negotiated pricing, vendor terms, and business volumes — with no
authentication at all. This is a cross-tenant leak *and* an invariant-8 cost-visibility
leak, reachable from an unauthenticated browser.

**Fix applied to the contract:** store originals outside the web root
(`INVOICE_STORAGE_DIR`, defaulting to `./var/invoices/`, sibling to the app, never under
`public/`). Serve exclusively through an authenticated route handler that ownership-checks
`(organization_id, invoice_id)` and streams the bytes. Added an explicit standing rule
that no invoice byte is ever placed under `public/`.

### 2. [critical] Client-supplied ids can cross tenant boundaries

**Where:** `03-program-design.md` — `ReviewInput`, and the approval call stack
**Claim:** `ReviewInput` accepts `invoice_id` and per-line `matched_product_id`; approval
later writes cost to that product after only `requireRole("owner")`.

A foreign key proves a row exists, not whose it is. A manipulated `matched_product_id`
pointing at another tenant's product would attach to the attacker's invoice line and, on
approval, **overwrite that other tenant's catalog cost**. The proposed child tables
(`invoice_line`, `extraction_job`, `audit_packet_file`) also omitted `organization_id`
entirely, so there was no column to scope by even if someone remembered to.

This is the exact gap already found once in this repo, where an unchecked `locationId`
leaked another tenant's location name — and invariant 9 was written because of it.

**Fix applied to the contract:** every child table carries `organization_id` and a
composite `(organization_id, parent_id)` foreign key, matching the convention already in
`db/schema.ts` (`product` → `vendor`, `count_line` → `count`). Every domain function
takes `Actor` rather than a bare `orgId`. Every nested id is ownership-checked, not
existence-checked, returning `NotFoundError` on a cross-tenant miss. Added two-tenant
rejection tests to the test plan.

**Second pass, same day — four references the first correction missed.** Re-auditing
`02-architecture.md` against the structural rule the correction itself states ("*every*
child table carries a composite `(organization_id, parent_id)` FK, *every* domain function
takes `Actor`") found four places that did not follow it:

| Missed | Why it mattered |
|---|---|
| `vendor_alias` had **no tenant FK at all**, on either `vendor_id` or `matched_product_id` | The worst of the four. Both ids arrive from the client on the review screen, and an alias *persists* — it is rung 1 of the matching ladder, so one bad `matched_product_id` is silently re-applied to every future invoice from that vendor, growing more trusted as the UI stops flagging a high-confidence match |
| `invoice.vendor_id` had no composite FK | Supplied by a client picker at upload; without it an invoice files against another tenant's vendor and every archive and audit-packet query then reports it under that name |
| `audit_packet_file.source_id` is polymorphic, so **no FK can guard it** — and the doc did not say so | This is the single spot in the audit-packet path where AR-3 rests on application code rather than a constraint. Precisely where the leak lived. Now stated, with the two compensating controls named as required rather than optional |
| Four query signatures still took a bare `orgId` | A bare `orgId` scopes the row being written but proves nothing about the *other* ids in the call — it is the existence-vs-ownership gap wearing the right-looking parameter |

Also corrected: flow C now shows the ownership check it was promising in the endpoint
table, as one batched `assertProductsOwned` *before* any write rather than per-line inside
the loop — a partial reject mid-loop would leave some lines and aliases written and some
not. And the check belongs at review, not only at approval: approval is where a bad id
overwrites cost, but review is where it gets *persisted into the alias table*.

`03-program-design.md`'s `findAlias` / `upsertAlias` / `matchLinesToProducts` signatures
were corrected to match, and three tests added (`alias_refuses_cross_tenant_product`,
`alias_refuses_cross_tenant_vendor`, `invoice_refuses_cross_tenant_vendor`).

The lesson generalises past this feature and is worth more than the four fixes: **stating
an invariant in a document does not apply it.** The first correction wrote the rule
correctly at the top of the data section and then, sixty lines later, defined tables that
did not follow it. Same failure mode as the finding itself — the rule was assumed to
propagate. A structural rule needs a mechanical sweep of every instance, not prose.

### 3. [critical] Audit packet bulk export is not organization-scoped

**Where:** `04-slices.md` — Slice 5, `buildAuditPacketJob`
**Claim:** The job was specified to query `invoice` rows *solely* by
`invoice_date >= dateFrom AND invoice_date <= dateTo`.

No organization predicate. Tenants share a calendar, so the first owner to request a
packet gets a ZIP containing **every organization's invoices** for that date range,
plus a signed download link emailed to them. The same slice promised counts in the ZIP
but defined no tenant-scoped count query at all.

This is the worst of the three: it is a bulk, durable, exportable leak that arrives in
an inbox, and the feature would look like it worked perfectly.

**Fix applied to the contract:** the job loads its packet by
`(packet_id, organization_id)` and carries that organization predicate through every
invoice, count, product, and file query. The manifest asserts a single distinct
`organization_id`. Added a two-tenant overlapping-date ZIP-content test.

### 4. [high] Approval can partially apply or replay cost changes

**Where:** `02-architecture.md` flow D / `03-program-design.md` approval call stack
**Claim:** Approval loops product updates and history inserts, *then* marks the invoice
approved — with no transaction, no row lock, no conditional state transition, and no
idempotency key.

Three failure modes: a crash mid-loop leaves some products repriced and the invoice
still `reviewed`, with no record of which; a double-click applies the invoice twice and
duplicates history; a retry re-derives costs from an already-approved invoice. Cost
data that is half-applied is worse than not applied, because valuation still produces a
confident number.

Invariant 5 already established that this project's answer to retried writes is an
append-only ledger with a unique key, not "hope it doesn't happen twice."

**Fix applied to the contract:** the whole approval runs in one `db.transaction`. The
status transition is a conditional compare-and-set (`WHERE status = 'reviewed'`) whose
zero-row result means "already applied" and returns the original success. Cost history is
uniquely keyed on `(source_invoice_line_id)` so a replay rolls back rather than
duplicating. Added crash-midway and concurrent-approval tests.

### 5. [high] The migration plan references schema objects that do not exist

**Where:** `03-program-design.md` — approval flow, and the new-tables list
**Verified against the live schema during this review:**

| Plan said | Reality (`db/schema.ts`) |
|---|---|
| add new table `vendor` | **already exists** — line 300, with a composite tenant unique index |
| `UPDATE product.unit_cost` | column is **`current_unit_cost`** — line 393 |
| `product.unit_cost_updated_at` | **no such column** |
| `INSERT INTO cost_history` | **no such table**, and none in the plan's own new-table list |

Following this contract produces either a failing migration or, worse, a migration that
silently invents a second vendor table. The cost-provenance table the whole feature
depends on was referenced twice and never designed.

**Fix applied to the contract:** reuse the existing `vendor` table (dropped from the new
list; the plan now notes only the columns being added to it). Renamed every reference to
`current_unit_cost`. Explicitly designed `product_cost_history` as a first-class new
table with tenant scoping and the idempotency key from finding 4. Added a standing rule
that Gate 3 must be reconciled against the live Drizzle schema before approval, and that
migrations are generated by drizzle-kit rather than described in prose.

### 6. [high] Upload and extraction use incompatible job states

**Where:** `03-program-design.md` `ExtractionJobStatus` vs `04-slices.md` Slice 1 vs the
Gate 2 cron
**Claim:** The enum declares `pending | classifying | extracting | ocr | done | failed`.
Slice 1 writes **`ready_for_classify`** — a value not in the enum. The cron claims
**`pending`**.

Two defects. First, `ready_for_classify` is undeclared, so MariaDB rejects the write
(or, if the column were widened to varchar, accepts a value nothing matches). Second,
and quieter: the job is created with status `pending` *at the same moment the invoice row
is created* — which is **before the client has finished uploading the file**. The cron
claims `pending` every 2 minutes. It will therefore claim jobs whose file does not exist
yet, and fail extraction on a missing object, for reasons that look like OCR flakiness.

**Fix applied to the contract:** one state machine,
`awaiting_upload → queued → running → done | failed`, declared once and referenced
everywhere. The job is created `awaiting_upload`; it only moves to `queued` after the
upload is confirmed *and* the stored object's size and SHA-256 are verified against what
was declared. The cron claims atomically with a conditional update so two workers cannot
claim the same job. Added an upload-before-queue ordering test and a concurrent-claim
test.

### 7. [high] Manager review contradicts the cost-visibility invariant

**Where:** `02-architecture.md` — "Role perms: owner=full, manager=upload+review (no cost)"
**Claim:** Managers get review access but "no cost".

The review screen defined two sections earlier in the same document shows per-line gross,
discount, and net, invoice totals, and **price-jump exception badges**. All of that is
supplier cost data; a price-jump badge is a cost derivative that leaks the direction and
rough magnitude of a cost change even if the number were blanked. `lib/authz.ts:140`
already defines `canSeeCost()` as `role === "owner"`. The role contract as written is not
merely risky, it is **impossible to implement** — the screen cannot render and also not
show cost.

**Fix applied to the contract:** invoice review is owner-only, matching `canSeeCost()`.
Managers keep upload (they can photograph a delivery) and can see non-monetary invoice
metadata — vendor, date, invoice number, status, line descriptions and quantities — via a
separate server query that never selects a monetary column. Redaction happens in the
query, not in the component, so a future UI change cannot leak it. Added a role-shaped
payload test asserting no monetary field is present in the manager response.

## What changed as a result

`02-architecture.md`, `03-program-design.md`, and `04-slices.md` were corrected in place.
Gate 2–4 approval is **withdrawn pending re-approval** of the corrected contract —
recorded in `00-status.md`.

No implementation code was written; there was none to change.

## Standing lessons worth keeping past this feature

1. **A new subsystem does not inherit the invariants — it re-earns them.** Five of seven
   findings were re-introductions of rules this repo had already written down and paid
   for. The invariants list in `AGENTS.md` needs to be walked deliberately at each gate,
   not assumed.
2. **`public/` is not storage.** Anything under it is unauthenticated by construction.
3. **Gate 3 must be reconciled against the live schema.** Four schema references in an
   approved document were wrong; all four were mechanically checkable.
4. **Green static checks say nothing about an unbuilt design.** Typecheck, lint, and tests
   all passed while the contract contained three critical leaks.
