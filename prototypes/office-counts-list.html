Design decisions

  • Status pills map the five lifecycle states directly onto the three approved status colors: draft = neutral muted (not yet a stock/count status worth flagging), in_progress/submitted/reviewed = warning amber ("in progress / needs attention," an approved meaning per §3), closed = success green. No new color was invented for the five states.
  • Closed rows show "View only" with a small lock glyph instead of any edit affordance — directly implementing invariant 1 (closed counts are immutable). Every other status gets a text link ("Continue" or "Review") instead, so the *absence* of that link, not a disabled/greyed one, is what communicates immutability.
  • Total Value column follows the same "structurally absent for manager" pattern as the catalog table — a second header cell and a second per-row branch, not a CSS-hidden column. It also reads "Not valued yet" (not "$0.00") for any non-closed count, since count.total_value is genuinely null until a count is reviewed/closed (db/schema.ts comment on Count.totalValue).
  • Opened-by/closed-by use the same colored-initials-tile pattern as vendors elsewhere in the app for visual consistency — these are staff members, never photos (no file storage in the MVP).

Open questions

  • No server action lists counts yet. app/actions/reports.ts only exposes countSummaryAction (one count) and reorderListAction — there's no listCountsAction. This table's data shape (id, type, status, openedBy/closedBy names, startedAt/closedAt, totalValue) would need a new query joining count against user twice (opened_by, closed_by).
  • "Start count" button has no destination. Kicking off a new count session is presumably a counting-app (mobile) action, not a back-office one — worth confirming this button belongs here at all, versus the back office being read-only over count lifecycle and only the mobile app starts/continues counts.
