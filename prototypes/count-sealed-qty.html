Design decisions & open questions — count-sealed-qty.html

Decisions

  • ADD vs SET is an explicit segmented control, not two separate screens, so a manager who needs the correction path (`setCountLineQuantitiesAction`) doesn't have to leave the line they're already looking at. The active segment uses brand blue, which docs/design-system.md §3 explicitly sanctions for "selected/active states in nav and forms" — this is a UI mode, not a stock/count status, so amber (which would otherwise read as "in progress") is deliberately avoided here.
  • Cases and eaches are always two physically separate inputs (invariant 4) — the combined "62 units" figure is clearly labeled reference-only and is never round-tripped as a single value back to the server.
  • Correction mode starts from the current server value (5 cases, 0 ea — the "typed 5 instead of 3" scenario from CLAUDE.md), not from zero, because a SET is "dial this to the true number," not "add a delta." Add mode starts from zero because it's additive by design.
  • Numeric inputs double as the stepper's display — you can tap +/- for a small correction or tap directly into the number and type "12", since typing beats twelve taps for the 3–5 second/SKU target.

Open questions for the owner

  • How does a manager discover a line is currently 5 cases when they only intended 3? This screen assumes they already know (they navigated here specifically to fix it) — should there be a review/audit view that flags likely mis-entries (e.g., a value far outside par) so the correction path gets discovered rather than hoped-for?
  • Is "Save correction" strong enough wording, or does a SET need a harder confirmation step (e.g. "Replace 60 units with 36 units?") given it can silently erase a real observation if triggered by mistake?
