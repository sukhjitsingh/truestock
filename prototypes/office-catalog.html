Design decisions

  • Owner and manager tables are two separate <table> elements in the DOM, toggled by the "Viewing as" control. The manager table never contains a Unit Cost <th>/<td> — satisfying divergence B5 (column absent, not CSS-hidden). In production these would be two TanStack Table column-def arrays selected by role, not one array with a hidden column.
  • Null current_unit_cost reads "Not entered" in muted italic — never "$0.00". This is the common case today (only the 9 draft kegs have real costs), so it had to look correct at scale, not like an edge case.
  • Case size reads "Not set" for every row because no product in the seed has case_size populated yet — same treatment, different reason (a data-completeness gap, not a role redaction).
  • Stock cell reconciles two rules that could read as contradictory: B1 says "no par → no bar, no status word"; the reference's own instinct is "0 units → no bar" (a 0-width bar is meaningless). Applied as: no par → units only; par + 0 on-hand → "Out" in negative with no bar; par + >0 on-hand → units + status word + bar.
  • Product active = false is shown as a dimmed row + a plain "· Inactive" caption, deliberately NOT a status pill — green/amber/red are reserved for stock/count status (design-system.md §3), and active/inactive is a record-lifecycle property, not a stock signal.
  • "Needs producer" uses the warning (amber) pill — "needs attention" is an approved meaning for amber per §3, and Merlot/Chardonnay are varietals without a producer, so they can't yet be scanned or costed.
  • Vendor is shown as a deterministic colored initials tile (not a photo/avatar) per divergence B4 — colors are drawn from the existing status/accent token set, not new hex values.
  • Density matches divergence B6: 57px rows, 32px row-menu button, 36px filter/header controls — no phone-sized tap targets here.

Open questions

  • Stock cell has no backing field. ProductSummary (lib/domain/catalog.ts) carries catalog metadata only — no on-hand quantity. The two-line stock cell the reference calls "the best idea in this shot" requires joining catalog rows against ProductPar and the latest closed count's on-hand (the same computation reorderList() already does). Is this screen meant to reuse that computation, or should the catalog table drop the stock cell entirely and point users to the reorder list for on-hand figures? Today, with zero closed counts, every row's on-hand would be 0 — worth deciding before this ships.
  • Vendor name resolution. ProductSummary.vendorId is an id; this screen needs it joined against listVendorsAction(). Fine as a client-side join, flagging it since no backend action currently returns products with vendor names inline.
  • "Needs attention" view tab is decorative here (not wired to real filter logic) — would need a real query (e.g. wine category with no producer field, or products with no barcode) once that's defined.
