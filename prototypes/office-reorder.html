Design decisions

  • The empty state is the default view, on purpose — this reflects reorderList()'s actual current return (asOfCountId: null, items: []) since no count has ever closed. It reads as a real, expected state ("close your first count to see this"), not a broken page.
  • A "Preview with a closed count" toggle reveals a second, explicitly-labeled mock so the grouped-by-vendor layout can still be reviewed — every section of that preview carries a persistent warning-colored banner saying it isn't live data, so it can't be mistaken for the real thing (this addresses the same "plausible but wrong" failure mode CLAUDE.md warns about, applied to the prototype itself).
  • "As of count #N — closed [date]" sits in its own banner directly under the page title, above the summary cards — this is the single most load-bearing line on the screen per divergence B2 ("do not label anything Current") and it needs to be seen before any quantity is read.
  • No cost or dollar figures appear anywhere on this screen. reorderList() genuinely has none to gate — par levels and quantities are the only inputs — so there's no owner/manager split needed here, unlike the other four screens.
  • Suggested-order quantities use a small filled badge (neutral, not a status color) since "you should order N of this" is an instruction, not a stock-status reading — the on-hand number itself, not this badge, is where success/warning/negative would apply if this screen also showed per-item stock status (it doesn't, to avoid redundant color coding against the reorder-worthy filter already applied).

Open questions

  • No per-item "mark as ordered" or export action exists yet. Once a real reorder list has items, does the owner need a way to check items off, print/export to a vendor, or send an order? Out of scope for MVP per CLAUDE.md, but this screen currently has no next action beyond reading the list.
  • Reorder point vs. par fallback. reorderList() already handles a null reorderPoint by falling back to par level as the threshold — worth deciding whether the UI should visually distinguish "using par as the threshold" from "has its own reorder point," since right now both render identically.
