    Design decisions & open questions — count-session.html

    Decisions

    • The primary action is role- AND status-derived, not just status-derived. `closeCountAction`/`reviewCountAction` require owner or manager — staff literally cannot call them. So at `submitted`/`reviewed`, a staff viewer sees no action bar at all, just a "waiting on someone else" note, rather than a disabled button. At `draft`/`in_progress`, all three roles can submit, since spec §4 says any counting role may do so.
    • At `closed`, the bottom action bar is not rendered — the demo literally removes the DOM node, not `disabled`-attributes it — per invariant 1's "not disabled, absent." A closed-count banner takes its place, explaining that corrections are a new adjustment, never an edit here.
    • Only `owner` sees the total-value line and the two-line CLOSE COUNT button. This is a stricter gate than the plain owner/staff split used elsewhere — CLAUDE.md's role table says manager has "no cost visibility" too, and `closeCountAction`'s own response only attaches `totalValue` `...(actor.role === "owner" ? {...} : {})`. Manager gets `totalUnits`/`pricedLineCount`/`excludedLineCount` (visible to everyone here) but never a dollar figure.
    • The excluded/unpriced-line count (33 of 42) is shown as an ordinary, unapologetic line in the progress card, per CLAUDE.md's "unpriced lines are normal, not errors" — most of the real catalog has no cost yet.

    Something the server actions made awkward — flagged for backend/owner

    • There is no live "progress totals" read. `getCountAction` returns raw lines; `totalUnits`/`pricedLineCount`/`excludedLineCount`/`totalValue` are only ever computed by `closeCount` (lib/domain/counts.ts), at the moment of closing. This screen's progress card and its "$1,842.60" while `reviewed` (not yet closed) is necessarily a value computed client-side by summing the returned lines — which means the client has to reimplement `summarizeValuation`'s logic to show a live total before close, and it can drift from the server's own computation if that logic ever changes on one side and not the other. Worth asking: should `getCountAction`/a new endpoint return the same summarized totals `closeCount` computes, read-only, before the count is actually closed?

    Open questions for the owner

    • Should staff be able to see the timeline/progress view at all once they've submitted, or does "nothing left for you to do here" mean the whole session should just disappear from their list?
    • Cancelling a count entirely (not shown here) isn't in the five server actions this screen was built against — is "cancel a count" in scope, or does an unwanted count just stay `draft` forever?
